# Plan: Add `protor update` Command

## Overview
Add a new CLI subcommand `protor update` that checks for the latest version on PyPI and optionally upgrades the protor package to the latest release.

## Implementation Details

### 1. New Module: `protor/updater.py`
Create a dedicated module to handle update logic, keeping it separate from CLI parsing.

**Functions:**
- `get_current_version() -> str`: Returns currently installed version (reuse `__version__` from `__init__.py`)
- `get_latest_version() -> str`: Fetches latest version from PyPI JSON API (`https://pypi.org/pypi/protor/json`)
- `check_for_update() -> dict | None`: Compares versions, returns `{"current": "...", "latest": "...", "update_available": True/False}` or `None` if check fails
- `perform_update(dry_run: bool = False) -> bool`: Executes `pip install --upgrade protor` via subprocess, returns success status
- `_is_editable_install() -> bool`: Detects if installed in editable/dev mode (check if source dir is in `protor.__file__` path)
- `_is_pip_install() -> bool`: Detects if installed via pip vs source

**Key Design Decisions:**
- Use `requests` library (already a transitive dependency via analyzer.py) for PyPI API calls
- Use `subprocess.run()` to invoke pip for self-upgrade
- Handle network errors gracefully with timeouts
- Parse version strings using `packaging.version` (standard pip dependency, always available)

### 2. CLI Integration: `protor/cli.py`

**Changes:**
- Add `_cmd_update(args)` handler function
- Register new subparser in `_build_parser()`:
  ```python
  up = sub.add_parser("update", help="check for updates and upgrade protor")
  up.add_argument("--check", action="store_true", 
                  help="only check for updates, don't install")
  up.add_argument("--yes", "-y", action="store_true",
                  help="skip confirmation prompt")
  up.set_defaults(func=_cmd_update)
  ```

**Handler Logic:**
1. Check for update availability
2. If `--check` flag: print version info and exit
3. If no update available: print "Already up to date" message
4. If update available:
   - Show current vs latest version
   - Ask for confirmation (unless `--yes` flag)
   - Call `perform_update()`
   - Show success/failure message with appropriate hints

### 3. Error Handling

**Scenarios to handle:**
- Network unavailable when checking PyPI
- PyPI API returns unexpected format
- Permission denied during pip upgrade
- Editable install detected (warn user to update via git pull)
- pip not found in PATH
- User cancels the update

**User Messages:**
- Success: "✓ protor updated to v{version}"
- Already current: "✓ protor is already up to date (v{version})"
- Editable install: "⚠ Editable install detected. Update via: git pull && pip install -e ."
- Network error: "✗ Failed to check for updates. Check your internet connection."
- Permission error: "✗ Permission denied. Try: sudo pip install --upgrade protor"

### 4. Testing: `tests/test_updater.py`

**Test Cases:**

- `test_check_for_update_update_available`: Mocks newer version on PyPI

- `test_perform_update_success`: Mocks subprocess.run success

- `test_cmd_update_check_flag`: Tests CLI --check behavior
- `test_cmd_update_yes_flag`: Tests CLI --yes auto-confirm
- `test_cmd_update_no_update_available`: Tests up-to-date scenario

## Dependencies
- No new dependencies required
- Uses existing: `requests` (transitive), `subprocess` (stdlib), `packaging` (pip dependency)

## Edge Cases
1. **Editable installs**: Detect and warn users to update via git
2. **Virtual environments**: Update works within active venv
3. **Permission issues**: Provide helpful error messages with sudo hint
4. **Network failures**: Graceful degradation with clear error messages
5. **Concurrent updates**: pip handles locking, we just report status
